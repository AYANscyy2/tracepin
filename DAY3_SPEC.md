# Day 3 Spec — Root Cause, Repro, Viewer, README (`tracepin`)

Two halves and a write-up. Morning is the TraceRoot half (finding → source → commit →
runnable repro). Afternoon is the full-stack requirement (Next.js trace viewer).
Evening is the README, which is the artifact that actually gets you the interview.

Budget honestly: if you fall behind, cut viewer scope — `/compare` is the first to go,
the waterfall is the last. Never cut the README.

## Morning — `rootcause.py` + repro generation (~4h)

### The chain you're building

```
Finding → span → code.file.path:code.line.number → source snippet
                                                 → git blame → commit, author, date
                                                 → GitHub permalink
                                                 → runnable repro script
```

Day 2's `code_location` already gets you two hops in. The new work is blame, snippet
extraction, and repro emission.

### `rootcause.py`

```python
class CodeContext(BaseModel):
    file: str
    line: int
    function: str
    snippet: str            # ±8 lines around the hit, with line numbers
    blame: BlameInfo | None
    permalink: str | None   # github.com/<repo>/blob/<sha>/<path>#L<line>


class BlameInfo(BaseModel):
    commit: str
    author: str
    authored_at: datetime
    subject: str            # commit message first line
```

Blame via subprocess, porcelain format so it parses cleanly:

```python
def blame_line(path: str, line: int, sha: str = "HEAD") -> BlameInfo | None:
    out = subprocess.check_output(
        ["git", "blame", "-L", f"{line},{line}", "--porcelain", sha, "--", path],
        text=True, stderr=subprocess.DEVNULL,
    )
    # first token of line 1 is the commit sha; then key/value lines:
    # author, author-time, author-tz, summary
```

Use the run's recorded `vcs.repository.ref.revision` as the blame ref, not `HEAD`. The
trace was produced by that commit — blaming HEAD gives you today's code, which may not be
what ran. Getting this right is a small detail that a reviewer who works on exactly this
problem will notice.

Derive the permalink from `git remote get-url origin`, normalising SSH form
(`git@github.com:user/repo.git`) to HTTPS. Skip silently if there's no remote.

### Run-level root cause

Per-finding blame is useful. The stronger output is **aggregation**: group all findings by
`code_location`, and rank by how many distinct tasks each location breaks.

```
tracepin rootcause findings/run_v1.json

  Locations ranked by tasks affected

  1. tools/docs.py:36  search_kb          14 findings / 11 tasks
     blame  a3f91c2  Dev  2026-09-20  "add knowledge base search tool"
     "Search the knowledge base."          <- docstring is the entire tool contract
     github.com/.../tools/docs.py#L36

  2. tools/users.py:12  get_user           6 findings / 5 tasks
  ...
```

That top line is your headline claim: *one docstring, eleven broken tasks*. And you have
the v3 run proving that changing that one line fixed them. Make sure this command's output
reproduces that story cleanly — it's going in the README verbatim.

### `tracepin explain <trace_id>` — single-trace deep dive

For one trace, print in order: task prompt → findings with severity → the tool-call
timeline → the code context for the top finding → the suggested fix category. Keep the
"suggested fix" honest and rule-based, not LLM-generated:

| detector | fix category |
|---|---|
| `args.schema_invalid` (clustered on one tool) | tool description / schema docs |
| `loop.repeated_call` with identical args | prompt: handle error feedback |
| `tool.unknown_name`, distance ≤3 | rename confusable tools |
| `error.ignored` | prompt: surface tool failures |
| `perf.unaccounted_time` | instrumentation gap |

A hardcoded mapping is the right call here. An LLM-generated suggestion would be the
obvious move and it would be worse — unverifiable, and it undercuts a project whose whole
premise is deterministic detection. Say that out loud in the README; it reads as judgment.

### Repro generator

```
tracepin repro <trace_id> --out repro/t017_repro.py
```

Emits a standalone script that replays exactly one task:

```python
"""Repro: t017 — search_kb called with unnested args, 6x identical retries.

Generated by tracepin from trace 862eb66a6c820ce63dddc9f3da5487f9
Run 4f2a1b  model=gemini-2.0-flash-lite  prompt=v1  commit=a3f91c2

Expected failure:
  - 6x execute_tool search_kb, all ERROR, all identical arguments
  - stop_reason == "max_iterations"

Run:  python repro/t017_repro.py
Exit: 0 if the failure reproduces, 1 if it does not.
"""
```

Body: checkout-free — it pins model, prompt version and task, re-runs the agent, then
asserts the failure signature (detector ids that must fire). Print a diff if the signature
differs.

Two requirements:

1. **Assert the failure, exit non-zero if it *doesn't* reproduce.** A repro script that
   passes when the bug is gone is a regression test. That framing — "every bug my
   detectors find becomes a test" — is worth more than the script itself.
2. **Commit the generated repros** for your three case-study bugs, plus their recorded
   trace JSONL, so anyone can read them without an API key.

## Afternoon — Next.js viewer (~4h)

This exists because TraceRoot's posting requires React/TS/Node. Don't over-scope it.

### Setup

Next.js App Router, TypeScript, Tailwind. `web/` inside the same repo — one repo, one
story. No database: findings JSON and trace JSONL are copied into `web/data/` and read in
server components with `fs`. Static-exportable, deploys to Vercel with sample data
committed.

Types: hand-write `web/lib/types.ts` mirroring `models.py`. Do **not** generate them —
it's 60 lines and generated types will drift silently.

### Routes

```
/                    runs list: id, model, prompt version, pass rate, finding counts
/runs/[runId]        task table (id, prompt, pass/fail, findings) + detector summary
/traces/[traceId]    waterfall + findings + code panel      <- the hero
/compare             v1 / v2 / v3, the regressed/fixed/still-failing buckets
```

### `/traces/[traceId]` — spend your effort here

Three panes:

- **Waterfall.** Spans as horizontal bars positioned by `start_ns` offset, width by
  duration, nested by depth. Flagged spans marked. Hover shows the attribute set. This is
  the only component worth real polish — it's the screenshot that goes at the top of the
  README.
- **Findings list.** Click a finding → its `span_ids` highlight in the waterfall. That
  interaction is the whole point of having built a UI rather than a CLI; make sure it
  works before you style anything.
- **Code panel.** Source snippet from `code_location` with the implicated line marked,
  blame line above it, GitHub permalink out.

Render the unaccounted-time gaps as hatched/empty regions between bars. Your 60s gap
becomes visually obvious rather than a number in a table — that's the argument for the UI
existing, made visually.

### Design direction

Subject matter: a measurement instrument for agent failures. The bars **are** the data, so
they carry the only saturated colour on the page; everything else stays quiet.

- **Base:** cool light neutral (`#F6F7F9`), ink (`#14161A`), rule (`#DFE2E7`). Not a warm
  cream — that palette is the current AI-design default and it reads as one.
- **Accent:** one hue for normal span bars (a desaturated teal-slate, `#3E6B70`), one for
  error (`#B8422E`). Severity uses weight and a marker, not three more colours.
- **Type:** one grotesque for UI (Inter is fine — it's genuinely the right tool for dense
  data UI), one mono for span ids, durations, attribute keys and source. Mono here is
  functional, not decoration: these are values you compare character by character.
- **Density over air.** A trace viewer that needs scrolling to see 12 spans has failed.
  Tight rows, hairline rules, no cards. Skip the rounded-card grid entirely.
- **No entrance animations.** Motion only on interaction: selecting a finding, expanding a
  span. Anything else reads as template.

Quality floor, no announcing it: keyboard focus visible, works at 1280px, respects reduced
motion.

## Evening — README (~2h)

The highest-leverage two hours of the three days. Most people opening this repo read the
README and nothing else.

### Structure

```
# tracepin

One sentence: what it does.
[waterfall screenshot, a flagged trace]

## The case for it
3-4 sentences. Agents fail in ways logs don't capture — loops, ignored errors,
schema drift. OTel spans + deterministic detectors make those failures countable
and attributable to a line of source.

## What happened when I ran it
The v1 → v2 → v3 table. Numbers, not adjectives.

## Three bugs it caught
The case studies. Each: what fired, the trace, the root cause, the fix, the proof.

## How it works
Instrumentation → detection → root cause → repro. One diagram, short.

## Detectors
Table: id, what it catches, how, known false-positive mode.

## Run it
Commands that work against committed sample data, no API key needed.

## Design notes
The judgment calls. This section is where you sound like an engineer.
```

### The three case studies

1. **search_kb schema** — 14 invalid-arg events across 11 tasks, all tracing to one
   docstring. Root cause command output, the one-line diff, and 41→43 after. This is the
   strongest because the bug was in *your* code, found by *your* tooling, and the fix is
   proven by a regression run.
2. **Identical retries** — the model re-sent byte-identical args six times after a
   validation error. Prompt-level fix, 35→41. Shows the detector distinguishing a model
   behaviour bug from a code bug.
3. **The 60s of unaccounted time** — 1m11s wall clock, ~10s of spans. Found by looking at
   a waterfall, now caught automatically by `perf.unaccounted_time`. Shows you can find a
   class of bug that logging can't.

Add a fourth short one if you want: **t024**, where the detector signature stayed identical
across all three runs and the actual bug turned out to be in your checker, not the agent.
"My tooling found a bug in my test harness" is a good, honest note — and it explains the
44th task instead of leaving it unexplained.

### Design notes section

Four or five bullets, each a decision and its reason:
- Real OTel semconv, not a custom JSON format — why, and which version you targeted.
- Both old and new `code.*` attribute names, because the semconv moved.
- Deterministic detectors over an LLM judge — reproducible, no API cost in CI, testable.
- Blame against the run's recorded commit, not HEAD.
- Failed tool calls emitted as spans rather than swallowed — the decision that made every
  detector possible.

That list is the strongest thing in the README. It's the difference between "built a tool"
and "made a series of defensible engineering choices," and it's what an interviewer will
open the conversation with.
